# MAIN WEBEE WEB APP / BACKEND PROMPT — Canonical Notification & Capability System

Extend the existing WEBEE main web application/backend so that notification configuration, workspace capability detection, HiveMind/SystemMind notification management, lead filtering, recipient rules and human sales-agent assignments are handled centrally.

This main WEBEE backend must become the **single canonical source of truth** for both the web app and mobile app.

## CRITICAL RULE

Do NOT build a separate mobile notification/business-logic system.

The mobile app will consume the APIs/services created here.

Before changing anything:

1. Audit existing HiveMind settings.
2. Audit existing SystemMind settings.
3. Audit existing AccountsMind settings.
4. Audit current workspace/account settings.
5. Audit existing notification tables/services.
6. Audit existing in-app notification logic.
7. Audit existing Expo/push notification backend logic.
8. Audit workspace roles and sub-accounts.
9. Audit lead filtering and assignment fields.
10. Audit workspace-specific/custom data sources.

Reuse existing infrastructure wherever possible.

Do NOT replace working systems.

---

# 1. CENTRAL NOTIFICATION ENGINE

Create or extend ONE canonical backend notification engine.

All notification-producing events must flow through this service.

Required logical flow:

**Event occurs**
→ resolve workspace
→ identify notification type
→ check workspace capability
→ load workspace notification policy
→ evaluate filters
→ resolve recipients
→ apply user preferences
→ deduplicate event
→ create durable in-app notification
→ dispatch enabled channels
→ record delivery result

Do not scatter independent notification-send logic throughout webhook handlers.

---

# 2. WORKSPACE CAPABILITY ENGINE

Create or extend a canonical resolver such as:

`getWorkspaceCapabilities(workspaceId)`

It must inspect real workspace configuration, enabled products, agents, integrations and services.

Possible capabilities include:

* leads
* qualification
* sentiment
* bookings
* calendar
* calls
* inbound receptionist
* outbound lead generation
* campaigns
* reports
* BuzzChat
* WhatsApp
* Follow-Up Centre
* HiveMind
* GrowthMind
* SystemMind
* AccountsMind
* email
* CRM
* human sales agents
* lead assignment
* deployed AI agents

Do not infer capabilities simply because a frontend menu exists.

---

# 3. AUTOMATIC PROVISIONING

Whenever:

* a workspace is created
* onboarding is completed
* a service is activated
* an AI agent is deployed
* BuzzChat is connected
* a CRM is connected
* calendar functionality is enabled
* campaigns become available
* Follow-Up Centre is enabled
* another WEBEE product/module is added

rerun workspace capability analysis.

Automatically provision any newly applicable notification definitions.

This must be:

**incremental**

and

**idempotent**

Running it repeatedly must NOT:

* duplicate settings
* reset existing choices
* reset existing filters
* change recipients unexpectedly

# 5. DEFAULT NOTIFICATION BEHAVIOUR

Use sensible defaults.

Examples of important events that can default ON:

* qualified lead
* booked appointment
* lead assigned
* campaign failure
* integration failure
* workflow failure

Potentially high-volume events should be optional/default OFF unless existing settings already specify otherwise:

* every new lead
* every campaign completion
* routine reports
* low-priority informational events

Do not change existing client choices.

# 12. HIVEMIND ROLE

Extend existing HiveMind functionality without changing its current settings/autonomy architecture.

HiveMind should act as the operational intelligence layer.

It should be able to identify things such as:

* qualified leads arriving with notifications disabled
* booked leads not reaching sales agents
* BuzzChat replies going unnoticed
* sales users receiving inappropriate notification volume
* notification filters that appear operationally ineffective

HiveMind can recommend changes.

If existing HiveMind operator/autonomy permissions allow action, it may instruct SystemMind to apply the change.

If approval is currently required, keep that approval requirement.

Do NOT alter existing HiveMind autonomy rules.

---

# 13. SYSTEMMIND ROLE

Extend existing SystemMind functionality without rebuilding it.

SystemMind should act as the technical operator for notification infrastructure.

It should be able to:

* inspect workspace notification configuration
* detect missing notification definitions
* detect missing event sources
* provision settings when services are added
* validate filters
* validate recipient configuration
* validate push plumbing
* validate web/mobile notification parity
* repair missing configuration where existing SystemMind permissions allow

Use the existing SystemMind execution model.
